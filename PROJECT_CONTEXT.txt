1. PROJECT OVERVIEW & CORE VISION
--------------------------------------------------------------------------------
Logisim-evolution+ is a modernization fork of Logisim-evolution (a digital logic
simulator and design tool). The primary goal of the project is to elevate the
classic Java Swing application into a clean, modern, state-of-the-art tool
inspired by modern Linux desktop design languages (e.g., GNOME / Libadwaita
principles: dark mode ergonomics, pill controls, refined hierarchy, high-DPI
vector iconography, and calm contrast), while maintaining full compatibility
with existing Logisim circuit files (.circ), simulation semantics, and workflows.

Key Architectural Principles:
1. Pure Java Swing Implementation: Even though the UI follows modern design
   patterns (Libadwaita / modern GNOME aesthetic), class naming avoids "libadw"
   or "gtk" prefixes. Clean, modular Swing/FlatLaf components are used instead.
2. Theme Symmetry: Both Dark Mode and Light Mode are first-class citizens.
   Light mode must remain visually pixel-identical to classic Logisim where
   expected, while Dark Mode provides a glare-free, high-legibility experience.
3. Preservation of User Data:
   - Export and print paths ALWAYS use the light palette on white backgrounds.
   - User-chosen attributes (LED colors, custom label colors, custom subcircuit
     drawings) are NEVER overwritten or altered.
   - Stored .circ files remain byte-compatible and clean.

Phase 4: Component Rendering on Dark Canvas (The Staged Implementation)
-----------------------------------------------------------------------
User Feedback & Audit:
- On the new dark canvas, gate bodies (AND, OR, NOT) and input switch bodies were
  drawn in pure solid black (`#000000`), making them nearly invisible.
- Value labels and switch bars were dark on dark.
- Wires and pin stubs used legacy saturated blue (`#0000ff`), lacking contrast.

Core Design Decisions Established (D1 - D5):
  D1. Do NOT change the return value of `AppPreferences.COMPONENT_COLOR` monitor
      (`PrefMonitorInt.get()`) directly, because it is used by Preferences UI.
  D2. Replace the old "0 is default" sentinel with an explicit boolean preference:
      `ADAPT_COMPONENT_COLOR` (default `true`). When `true`, component color
      resolves via `Palette.stroke()`. When `false`, use stored user color.
  D3. Export (PNG/GIF/JPG/SVG/TikZ) and Print must ALWAYS use the light palette,
      regardless of current UI theme.
  D4. Light mode canvas must remain identical to original.
  D5. User-chosen colors (LED color, custom labels, custom subcircuit drawings)
      are never overridden.

Stage 0 Follow-Up Answers:
  - 0.1: `Palette.withForceLightPalette` / `setForceLightPalette` did not exist;
         they were proposals.
  - 0.2: `Palette.current()` and `isDarkTheme()` did not consult a paint scope.
         In dark mode, exports previously leaked dark wire/label colors onto white
         canvases. Fixed via `ThreadLocal` paint scope.
  - 0.3: `ComponentGlyphCache` cache key previously lacked theme/adapt/scope. It
         is used exclusively for UI widgets, never for export or print.
  - 0.4: Confirmed no export or print path hops threads to EDT via `invokeLater`
         or uses parallel streams during painting.

Stage 1 Implementation (Completed & Verified):
  1. Paint Scope: Implemented reentrant `ThreadLocal<Integer> FORCE_LIGHT_DEPTH`
     scope (`enterLightScope()`, `withLightScope()`) in `Palette.java`.
     Enforced light scope in `ExportImage.java` (`ExportThread.run`),
     `Print.java` (`MyPrintable.print`), and `PrintHandler.java` (`print` & `exportImage`).
     `Palette.current()`, `Palette.of(context)`, and `AppPreferences.isDarkTheme()`
     all honor the light scope.
  2. Preference `ADAPT_COMPONENT_COLOR`: Added `PrefMonitorBoolean` defaulting
     to `true` in `AppPreferences.java`.
  3. Context-Aware Stroke: `AppPreferences.getComponentColor()` returns
     `new Color(COMPONENT_COLOR.get())` if `ADAPT=false`, and `Palette.stroke()`
     if `ADAPT=true` (`#E6E6E6` in dark mode, `Color.BLACK` in light mode/scope).
  4. Migration: Idempotent migration on preference load checks `componentColor`:
     - `0` (default) or `0xFF000000` / `-16777216` (legacy black) -> `ADAPT=true`.
     - Custom colors (e.g. blue, red) -> `ADAPT=false`.
  5. Preferences UI: Added "Adapt component colors to theme" checkbox in
     `WindowOptions.java`. While checked, the color button is disabled and
     previews the resolved theme color swatch. Unchecking writes the resolved
     color into the monitor if previously default.
  6. Reset Grid Colors: `setDefaultGridColors()` resets `ADAPT_COMPONENT_COLOR`
     to `true`.
  7. Replacement Across Painters: Replaced `new Color(AppPreferences.COMPONENT_COLOR.get())`
     with `AppPreferences.getComponentColor()` across 83 component painters
     (gates, plexers, arithmetic, memory, I/O, wiring, SoC).
  8. Glyph Cache: Updated cache key with `isDark`, `adapt`, and `forceLight`,
     and hooked preference listeners to flush cache on change.

3. REMAINING PLANNED STAGES (STAGES 2 - 6)
--------------------------------------------------------------------------------
CORE ARCHITECTURAL PRINCIPLE: "MODERNIZE WITH RESPECT FOR FUNCTIONAL TRADITIONS"
--------------------------------------------------------------------------------
Tradition with Purpose: In digital logic design (EDA), primary colors carry strict
electrical semantics on the canvas: Green (1/0), Red (Error), Blue (Floating / Unknown Z),
and Orange (Bit-width mismatch). Original Logisim used Magenta for the Attribute Halo
not arbitrarily, but so engineers never confuse an inspection halo with floating blue (Z)
wires or active signals.

The Evolution+ Rule: Whenever a legacy visual convention carries a real functional or
cognitive reason for existing, we preserve its semantic separation while modernizing its
tonal execution to fit the GNOME / Libadwaita palette (e.g. GNOME HIG Orchid #C061CB for
dark attribute halos, preserving Color.MAGENTA in light mode and light scopes).
